## 0. 結論（先に要点）

1. **データのライセンスは CC BY-SA 3.0**（リポジトリの `COPYING` の本文と README で確認済み）。帰属表示が必須で、改変したデータには継承（ShareAlike）がかかる。
2. **アプリのプログラム本体まで CC BY-SA になるわけではない**、と読むのが自然。CC BY-SA 3.0 は「Collection（編集物）」について、SA の対象を作品そのものに限っている（§4(a)(b) の末尾）。ただし、描画した結果の画面や、KanjiVG の字形に手を加えて作った画像やデータは継承の対象になる。どこまでが翻案（Adaptation）かには【曖昧】な部分が残る（§2.3）。
3. **付属の Python スクリプトの一部は GPL v3** で、データとはライセンスが別。今回の `fetch.py` は自作で、付属コードは一切コピーしていない。
4. 常用 2136 字は **すべて KanjiVG に収録されている**（欠けは 0 字）。常用分の SVG は合計 8.66 MB（gzip で約 1.3 MB）。部品ツリーの JSON は 554 KB（gzip で約 80 KB）。
5. 部品ツリーは Lv5（部品から組み立てる課題）や部品の強調表示にそのまま使える。一方で、**似た漢字の見分け（Lv1〜4）には木構造だけでは足りない**。たとえば「未」と「末」は木構造が完全に同じになる（§5.3）。

## 1. 概要

- 漢字 1 字を 1 つの SVG で表す。筆画を 1 本ずつ `<path>` で持ち、筆順どおりに並んでいる。筆画は `<g>` 要素の入れ子でまとめられ、部品の構造（どの部品がどこにあるか）も表している。
- 字形は日本の教科書体・楷書が手本で、明朝体やゴシック体ではない（[FAQ](https://kanjivg.tagaini.net/faq.html)）。筆順も日本式。
- 収録範囲は JIS 第 1・第 2 水準が中心で、一部それ以外の字もある（[files.html](https://kanjivg.tagaini.net/files.html)）。
- ファイル名は「Unicode のコードポイントを小文字 16 進 5 桁にしたもの」+ `.svg`。例: 侍 = `04f8d.svg`、𠮟 = `20b9f.svg`。
  - 異体字や別の筆順の字は、`04e14-Kaisho.svg` のように接尾辞が付く（[variants.html](https://kanjivg.tagaini.net/variants.html)）。
- 座標系は `viewBox="0 0 109 109"`。筆画は塗りなしの線（`stroke-width:3`、端と角は round）で描く。

## 3. データ構造

### 3.1 SVG 全体の骨格

```
<?xml ...?>
<!-- 著作権・ライセンスのコメント（約 1.3 KB。すべてのファイルに入っている） -->
<!DOCTYPE svg ... [ <!ATTLIST g kvg:element ... > ... ]>   ← kvg:* 属性を宣言する内部 DTD
<svg viewBox="0 0 109 109" xmlns:kvg="https://kanjivg.tagaini.net/">
  <g id="kvg:StrokePaths_04f8d" style="fill:none;stroke:#000;stroke-width:3;...">
    <g id="kvg:04f8d" kvg:element="侍">          ← 字全体
      <g id="kvg:04f8d-g1" kvg:element="亻" ...>  ← 部品（入れ子にできる）
        <path id="kvg:04f8d-s1" kvg:type="㇒" d="..."/>  ← 筆画（-sN の N が筆順）
  <g id="kvg:StrokeNumbers_04f8d">                ← 筆順番号の表示位置（<text>）
```

- **筆順**: `<path>` が文書の中に現れる順番が、そのまま筆順になる。id の末尾 `-sN` も同じ番号。
- **グループ**: `-gN` は 1 から始まる連番。
- `kvg:type` は筆画の種類（㇐、㇑、㇒ など）。末尾に付く英字（`㇑a` など）の意味は、公式に説明されていない（[known-problems](https://kanjivg.tagaini.net/known-problems.html)）。

### 3.2 `<g>` の kvg 属性（[svg-format.html](https://kanjivg.tagaini.net/svg-format.html)）

| 属性 | 意味 | 件数（全 SVG） |
|---|---|---|
| `kvg:element` | その部分と**見た目が**一番近い字 | 79,656 |
| `kvg:original` | 意味の上での元の字（亻 → 人、扌 → 手）。見た目と違うときだけ付く | 7,880 |
| `kvg:variant="true"` | 変形した形の部品（亻、扌 など） | 10,880 |
| `kvg:position` | 同じ親を持つグループの中での位置: `left` / `right` / `top` / `bottom` / `kamae` / `kamaec` / `nyo` / `nyoc` / `tare` / `tarec` / `middle`（文書上は ⿶ ⿵ 系の値もある） | 48,447 |
| `kvg:radical` | 部首である場合の、どの基準による部首か: `general`（一般）/ `tradit`（康熙）/ `nelson` / `jis` | 12,825 |
| `kvg:part` | 筆順の都合で部品が分かれたときの、何番目の断片か | 6,023 |
| `kvg:partial="true"` | その部品の筆画の一部しか入っていない | 1,038 |
| `kvg:number` | 同じ部品が複数あって、それぞれが分割されているときの識別番号（例: 圖） | 23 |
| `kvg:phon` | 音符（発音を表す部分）。値の形式は不統一で、説明もない | 1,396 |
| `kvg:tradForm`, `kvg:radicalForm` | ほとんど使われていない | 16 / 15 |

### 3.3 実例（常用 JSON からの抜粋。`s` は筆画番号の範囲）

**侍**（8 画）: `亻` + `寺`（`寺` はさらに `土` の上、`寸` の下）

```json
{"e":"侍","s":[1,8],"k":[
  {"e":"亻","p":"left","r":"general","v":1,"o":"人","s":[1,2]},
  {"e":"寺","p":"right","ph":"寺","s":[3,8],"k":[
    {"e":"土","p":"top","s":[3,5]},
    {"e":"寸","p":"bottom","s":[6,8]}]}]}
```

**持**（9 画）: `扌`（元の字は手）+ `寺`。**侍と違って、`土` と `寸` に position が付いていない**（データの不統一）。

```json
{"e":"持","s":[1,9],"k":[
  {"e":"扌","p":"left","r":"general","v":1,"o":"手","s":[1,3]},
  {"e":"寺","p":"right","ph":"寺","s":[4,9],"k":[{"e":"土","s":[4,6]},{"e":"寸","s":[7,9]}]}]}
```

**語**（14 画）: `言` + `吾`。`吾` の中の `五` は、筆順の都合で `二` が 2 つの断片（`pt`: 1 と 2）に分かれ、その間に `五` 自身の 2 画（9〜10 画目）が入る。

```json
{"e":"語","s":[1,14],"k":[
  {"e":"言","p":"left","r":"general","s":[1,7],"k":[{"e":"口","s":[5,7]}]},
  {"e":"吾","p":"right","ph":"吾","s":[8,14],"k":[
    {"e":"五","s":[8,11],"k":[{"e":"二","pt":"1","s":[8,8]},{"e":"二","pt":"2","s":[11,11]}]},
    {"e":"口","s":[12,14]}]}]}
```

**問**: `門`（`kamae`）の中に、`element` を持たないグループ（左半分と右半分）がある。常用分では、`element` のないグループが 1,264 個あった。

## 5. アプリでの使い方

### 5.1 Lv5（部品から組み立てる課題）

- ツリーの第 1 階層の子が、そのまま「組み立て用の部品」になる。例: 侍 = [亻 (left), 寺 (right)]。
- 常用 2136 字のうち **1,642 字**は、第 1 階層が「`element` を持つ 2 部品」の形をしている。子を持たない（それ以上分けられない）字は 57 字。
- 部品の画像は、**完成した字の SVG から、その部品に属する筆画だけを抜き出して描く**のがよい。座標は完成形の位置のままなので、正解の配置がそのまま分かる。
  - 「寺」を単独の字として描くと、侍の右側にある寺とは縦横の比率が違う。部品のカードを単独の字の SVG で作ると、はめ込んだときに形が合わない。
- 選択肢に入れる「間違いの部品」は、`element` を索引にすると集められる。例: 寺を含む常用字 = 侍 待 持 時 特 等 詩、青を含む常用字 = 情 晴 清 精 請 静。
- 部品の名前には `element` を使い、変形した部品（亻）と元の字（人）の対応は `original` で取れる。ただし、このアプリでは読みや意味を教えないので、画面には形だけを出せばよい。

### 5.2 部品の強調表示（「違う部分はどこ？」）

- 各グループの `s: [最初, 最後]` から筆画の番号が分かる。その範囲の `<path>` に別の色や太さを付ければ、部品を強調できる。
- `part` で分かれた部品（語の中の二）は、同じ `e` を持つ兄弟を集めて扱う。
- 2 字の間で「違う部分」を出すには、たとえば侍と持の第 1 階層を比べ、`e` が違う子（亻 と 扌）の筆画を強調する、といった方法が使える。

### 5.3 Lv1〜4（似た漢字を見分ける課題）への注意

- **部品ツリーだけでは、形の似た漢字を区別できない場合がある**。「未」と「末」は、どちらも「木 + 丿（筆画の範囲も同じ）」という同じ木構造になる。同じように、土と士、己のような単独の字は子を持たない。
- 違いは筆画の座標（長さや位置）にしか現れない。似た字どうしを組にするには、パスの幾何的な比較か、別の類似漢字データが必要になる。
- `element` は「見た目の近さ」で付けられている。そのため、朱、株、殊、珠、籍、耕、耗も、部品として「未」を含むと判定される。部品が同じでも、それが意味の上の共通点だとは限らない。

## 6. Web で描画するときの要点

1. **`<img src="04f8d.svg">` で表示する**: 最も簡単。ただし、筆画ごとの色分けやアニメーションはできない。
2. **インライン SVG**（React ならビルド時に変換しておく）:
   - XML 宣言、DOCTYPE（内部 DTD）、コメントは、HTML の中に埋め込めない、または不要なので取り除く。ただしライセンス表示は、別途アプリのクレジット画面に出す。
   - `kvg:element` のような名前空間付きの属性は、JSX には直接書けない。ビルド時にパースして、「筆画の `d` の配列と部品ツリー」の JSON に変換するのが扱いやすい（この JSON は翻案になり、CC BY-SA の対象）。
   - `viewBox="0 0 109 109"`、`fill="none"`、`stroke-linecap="round"`、`stroke-linejoin="round"`。表示サイズを変えても線の太さを保ちたいときは `vector-effect="non-scaling-stroke"` を使う。
3. **筆順アニメーション**: 各 `path` で `getTotalLength()` を取得し、`stroke-dasharray` と `stroke-dashoffset` を順番に 0 まで動かす、という定番の方法が使える（今回は要件外）。
4. **筆順番号**: `StrokeNumbers` グループの `<text>` の位置を使う。表示しないなら丸ごと落としてよい。
5. SVG の DTD の宣言（`http://kanjivg.tagaini.net`）と、ルート要素の `xmlns:kvg`（`https://kanjivg.tagaini.net/`）で、名前空間の URI が一致していない。XML パーサーによっては属性の名前空間が変わるので、パーサー側で名前空間の接頭辞を取り除いて扱うと安全（`fetch.py` はそうしている）。

## 7. 注意点と未確認事項

- **【曖昧】翻案の範囲**: 実行時に色付けした画面や、構造だけを取り出した JSON が CC BY-SA の「Adaptation」にあたるか（§2.3）。安全側の運用として、データは CC BY-SA で配布し、コードとはファイルを分ける。
- **【曖昧】SVG のヘッダーコメントを削ってよいか**: §4(a) の「keep intact all notices」を厳密に読むと、SVG のコピーごとに表示を残す必要がある。軽量化のために削るなら、アプリ全体の帰属表示と、同梱するライセンス文書で代わりに示すことになる。これで十分かどうかは解釈が分かれる。
- **【曖昧】リリースが pre-release かどうか**: GitHub API に接続できず、確認できなかった。タグと zip の実物と SHA-256 は確認済み。
- **データの不統一**: 侍と持で、`寺` の中の `土` と `寸` に position が付いているかどうかが違う。`kamae` や `middle` の使い方が一貫していないことは、公式も認めている。`phon` と `kvg:type` の英字の意味は説明がない。部首の判定（`radical`）は基準ごとに違い、問の門は `nelson`、口は `tradit` になっている。
- **`element` のないグループ**が、常用分だけで 1,264 個ある（門の左右など）。部品のカードを作るときは、これを飛ばすか、親の部品にまとめる必要がある。
- **異体字や筆順違いのファイル**（`-Kaisho` など）は取り込んでいない。教科書体を基準にするなら `main` だけで足りる、と考えている。
- **表内字体と通用字体**: 常用漢字表では「剝、𠮟、塡、頰」が正式。一般のフォントや入力では「剥、叱、填、頬」が使われることも多い。教材でどちらを出すかは決める必要がある。
- **付属コードの一部は GPL v3**。データ（CC BY-SA）とは別物なので、コードを取り込む場合は注意する。
- 常用漢字リストの出典である Unihan は Unicode License のデータ。今回はリストを作るためにだけ使い、再配布はしていない（JSON のキーに字が並ぶだけ）。
